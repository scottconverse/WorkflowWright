WorkflowWright

Agent workflows fail for structural reasons, not prompting reasons. WorkflowWright assigns each step to the cheapest resource that can actually do it — code, an agent, or a human — and compiles the result into artifacts that cannot drift apart.

Most broken pipelines come from two errors: assigning to agents what a five-line script does deterministically for free, and putting a human approval gate in the middle where it serializes everything at one person's availability. WorkflowWright makes the assignment explicit — then generates the design doc, the diagram, and the orchestrator code from one spec, so they cannot disagree.

One spec in, four artifacts out

// spec.json (fragment)
{
  "id": "build",
  "label": "Implement the plan",
  "kind": "agent",
  "model": "sonnet",
  "reads": ["plan.md", "verify-report.txt"],
  "max_attempts": 3,
  "on_exhausted": "human"
}
$ python3 render_workflow.py spec.json --out out
wrote out/ticket-to-pr-design.md
wrote out/ticket-to-pr.mermaid
wrote out/ticket-to-pr.html

A code node moves the ticket. Agents scout, plan, build. A deterministic verify step routes failures back to the builder — three bounded attempts, then a human. The diagram on the right is the renderer's actual output for this spec, embedded here as the inline SVG it produced.

Why the generated orchestrator is worth having

Deterministic Python drives; agents are separate processes. Retries are counted against the node a failure re-enters, not the checker doing its job. A retried agent resumes its session, so it gets the news of the failure instead of a cold restart. Every payload is a file, so one node can be rerun against fixed input. Prompts travel on stdin, immune to argv ceilings and shim truncation. Each of those is easy to get wrong by hand — and each is pinned by a test.
